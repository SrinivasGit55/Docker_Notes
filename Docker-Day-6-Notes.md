# Docker Day 6 — Multi-Service Docker Project and Jenkins CI/CD

## Project Overview

This project combines Docker image building, a container registry, Jenkins automation, Docker Compose configuration, and Docker Swarm deployment. The goal is to connect the Docker commands learned earlier into an end-to-end delivery workflow.

The lab architecture uses three EC2 instances as a Swarm cluster: one manager and two worker nodes. The manager can also host Jenkins, depending on available resources. In production, Jenkins and cluster management components should be sized and isolated appropriately.

## Architecture

```text
Developer / Git Repository
          |
          v
        Jenkins
     (CI Pipeline)
          |
          v
 Build Docker Image
          |
          v
 Push to Docker Hub
          |
          v
 Swarm Manager Node
    /          \
Worker 1      Worker 2
    \            /
   Service tasks / replicas
```

## Step 1 — Prepare Infrastructure

Provision the lab servers, install Docker Engine, confirm the Docker service is running, and initialize or join the Swarm cluster.

```bash
sudo systemctl enable --now docker
docker version
docker swarm init
docker node ls
```

On the worker nodes, use the join command and token generated by the manager. The exact join token and address are specific to the cluster and should not be copied into public documentation.

## Step 2 — Build an Application Image

Use the project's Dockerfile to build an image. For example:

```bash
docker build -t movies:v1 .
```

Test the image locally before publishing it. Tag the image with the registry namespace:

```bash
docker tag movies:v1 YOUR_DOCKERHUB_USERNAME/movies:v1
docker login
docker push YOUR_DOCKERHUB_USERNAME/movies:v1
```

Use meaningful, preferably immutable tags for release builds. Avoid depending on the mutable `latest` tag for controlled deployments.

## Step 3 — Jenkins Pipeline

A Jenkins pipeline can automate checkout, build, tests, image creation, publishing, and deployment. A simple stage flow is:

```text
Checkout Source
     |
     v
Build / Validate
     |
     v
Test
     |
     v
Build Docker Image
     |
     v
Push Image to Registry
     |
     v
Deploy / Update Swarm Service
```

The exact commands depend on the application's build tool and repository structure. Jenkins credentials should be configured in Jenkins Credentials and referenced securely; never hard-code registry passwords or access tokens in a Jenkinsfile.

## Step 4 — Compose Deployment Definition

A Compose file can define the services that make up the application. Example:

```yaml
services:
  movies:
    image: YOUR_DOCKERHUB_USERNAME/movies:v1
    ports:
      - "8080:80"
    deploy:
      replicas: 3
```

This is a Swarm-oriented example using the `deploy` section. Compose file compatibility differs between `docker compose up` and `docker stack deploy`; do not assume every Compose option is interpreted identically by both commands.

## Step 5 — Deploy to Swarm

From a manager node, deploy the stack:

```bash
docker stack deploy -c compose.yaml movies
```

Inspect the stack and services:

```bash
docker stack ls
docker stack services movies
docker stack ps movies
docker service ls
docker service ps movies_movies
```

Update the stack after changing the image tag or configuration by deploying the revised Compose file again.

## Step 6 — Scaling and Recovery

Swarm services can be scaled by changing their replica count:

```bash
docker service scale movies_movies=5
docker service ls
docker service ps movies_movies
```

Swarm attempts to maintain the declared number of tasks. This helps recover from task failure, but it does not replace health checks, monitoring, backups, or application-level recovery.

## Cleanup for a Learning Lab

Stop and remove only resources created for this lab. Check the stack before removal:

```bash
docker stack ls
docker stack rm movies
docker service ls
docker ps -a
```

After confirming no required workloads remain, remove unused images or other resources individually. Broad prune commands can delete data and should not be run blindly.

## Practical DevOps Workflow

This lab demonstrates the relationship between source control, Jenkins, Dockerfiles, image tags, registries, Compose configuration, and Swarm deployment. The pipeline makes the build and deployment process repeatable, while Swarm manages the desired number of running service tasks across cluster nodes.

The project is a learning lab. Running it does not by itself establish production readiness; security, secrets, monitoring, capacity, storage, networking, rollback strategy, and availability still need to be designed.
